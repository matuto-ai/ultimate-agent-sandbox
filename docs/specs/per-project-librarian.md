# Per-Project Librarian specification

Tracking issue: [Specify the per-Project Librarian knowledge layer](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/137). This complete specification is proposed for human review; the tracker issue is its shorter publication summary. Archive this document when the issue closes or every approved split implementation ticket closes.

## Problem Statement

Participants using different Runtimes need durable, human-legible Project knowledge that survives sessions and Room lifecycle changes. Working knowledge does not necessarily belong in the Project source repository, and a Runtime-specific memory extension is not a shared Project interface. Reads must remain deterministic, while explicit captures become useful integrated knowledge without blocking interactive work or falsely claiming that an unpushed draft is safe.

This specification consolidates the completed [Chart the per-Project librarian knowledge layer](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/30). Its decision tickets are the source of authority; this synthesized specification awaits human approval before decomposition. The [Hermes inventory](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/36#issuecomment-6397330903) did not establish context reduction as a reason to build this service. The historical observation of eleven Project rows after 148 sessions is not a current usage measurement, and the assumption that cross-Runtime access will improve capture remains unverified. Keep the first version narrow enough that low adoption is inexpensive.

## Solution

Provide one external singleton Library Service that owns a private working clone, publishes to one qualifying private canonical Git repository, and maintains independent OKF v0.2 bundles for Projects. The repository is a storage contract, not a requirement for GitHub, Gitea, another Forge, or a subscription. Participants read their Project through an atomically published read-only file projection and submit explicit drafts through a Project-scoped Hub Command. The service commits drafts before acknowledging them, performs one globally serialized bounded synthesis attempt at a time, and submits every content change through one deterministic commit gate.

Use native Markdown lookup, not a memory engine, derived search index, or general-purpose consolidation framework, as settled in [Evaluate memory-engine reuse before specifying Librarian internals](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/46#issuecomment-6397339230). Human controls cover bounded conflict inspection, adjudication, operational settings, and recovery. Lint is deterministic and non-destructive; semantic maintenance uses ordinary explicit drafts. Promotion into sandbox-wide guidance remains an ordinary separately authorized human handoff.

This is a sibling Library scope, not a new dependency or expansion of the main product first delivery. The main product remains GitHub-first. Existing trusted-infrastructure, Room, Participant, Hub, and Manager authority boundaries remain intact.

## User Stories

1. As a Participant using any supported Runtime, I want to discover accepted and pending Project knowledge through native files, so that I can recover context without a model-backed read service or automatic prompt injection.
2. As an authorized Participant, I want to submit a small explicit draft and retry it safely, so that valuable knowledge survives without duplicate capture or blocking my Run when storage is unavailable.
3. As a Project-authorized human, I want empty registration and an explicit source-pinned import preview, so that existing documents do not silently become accepted knowledge.
4. As a Project-authorized human, I want to inspect conflicting claims and submit my conclusion and rationale, so that unresolved knowledge can be resolved without giving the model authority to reinterpret my decision.
5. As an installation operator, I want scoped controls, literal health observations, and versioned shared settings, so that I can operate and recover the Library without direct clone editing or exposing Project content in diagnostics.
6. As a Project owner, I want repository isolation, explicit model-egress authorization, visible provenance and trust signals, and controlled disclosure, so that knowledge sharing does not silently enlarge authority or audiences.
7. As a Project maintainer, I want bounded structural checks and deliberate repairs, so that stale, isolated, or contradictory knowledge is visible without automatic erasure or unsupported semantic changes.
8. As an operator, I want acknowledged drafts and history to survive process, transport, and Room failures, with archival and restoration preserving pending work, so that lifecycle operations do not destroy knowledge.

## Acceptance Criteria

1. **Repository and ownership:** A configured private Git target qualifies without a mandatory hosting platform. The non-admin Library identity is the only ordinary writer, can publish ordinary fast-forward commits, cannot rewrite or delete Library branch refs or administer/delete the repository, and cannot write source repositories. The canonical target and working clone remain distinct and outside Rooms. Unknown or invalidated target qualification blocks Library writes.
2. **Project authority:** Project and Actor attribution come from authenticated authority, not payload paths or claimed identities. Cross-Project reads, writes, source resolution, model assembly, inspection, and actions are rejected. Every retry rechecks current authority. The only additional cross-Project configuration effect is an explicitly authorized shared-settings change, not access to other Project content.
3. **Registration and import:** A new Project receives exactly the six-file empty skeleton in one pushed initialization commit. Exact retries create no additional commit or log entry. Identity conflicts, malformed or partial bundles fail closed without overwrite. Import requires a human-confirmed manifest at a pinned source commit, creates bounded drafts rather than accepted concepts, and deduplicates the same confirmed manifest.
4. **Read projection:** Each visible bundle and its snapshot metadata identify one coherent published commit. Failed refresh retains the previous coherent publication and timestamp; before the first publication, the bundle is absent and the manifest reports a null commit. Projection lag does not turn durable capture into failure, and capture responses distinguish durability from visibility.
5. **Deterministic retrieval:** Browse authored indexes and scan native files with case-insensitive AND substring matching. Only no-document results permit explicitly labelled typo-tolerant fallback. Return at most eight initial matches, fragments first, with whole-document follow-up for authoritative metadata and context. Matching pending entries remain visibly DRAFT; fallback entries are FUZZY; no match yields no inferred answer. No model or derived index participates in reads.
6. **Explicit capture and retries:** Only deliberate submissions enqueue knowledge. Valid structured captures receive DURABLY_QUEUED only after their exact draft commit is published; deterministic failures receive REJECTED and infrastructure/uncertain acceptance receives the retryable NOT_DURABLE contract. Same librarian request ID plus the same canonical payload creates no duplicate; different payload under that ID returns ID_CONFLICT. A new Hub Command ID may retry the same librarian ID under current authority without changing immutable submission provenance. Capture failure does not prevent Run completion or context reset.
7. **Bounded fair synthesis:** One global model attempt runs at a time; Git write serialization does not hold the lock while awaiting the model. Eligible Projects receive deterministic fair turns, and each attempt yields. Initial ceilings are eight drafts, 64 KiB of draft content, and 120 seconds per attempt. A fixed drain batch retains its queue IDs across ordinary retries. Later drafts do not enter that batch.
8. **Model and source boundary:** Only a qualified, explicitly selected local or Project-authorized hosted profile processes the selected Project material. The request contains selected drafts, permitted accepted Project knowledge, and explicit pinned bounded source excerpts, with no unselected drafts, sibling content, history, audit, credentials, transcripts, or arbitrary source files. Invalid, unauthorized, secret-blocked, or oversized inputs make no model call. There is no silent provider fallback, truncation, browsing, or model tool access.
9. **One write gate:** Registration, import, enqueue, integration, adjudication, reconstruction, archival, and restoration validate the complete proposed Project result atomically. Invalid text, YAML, paths, content, metadata, provenance, or bounds produce no content commit. The model supplies only a constrained proposal; deterministic code constructs files, metadata, indexes, and log entries. Accepted concepts are never automatically deleted or renamed.
10. **Trust and uncertainty:** Stored content is reference data, never instruction authority. Integrated status, verification, freshness, provenance, and derived OKF trust tier remain distinct. A model cannot verify its own output or set freshness by inference. Meaningful content changes clear current verification. Unsupported contradictions park attributable drafts while unrelated valid work can proceed; uncertain attribution causes no partial commit.
11. **Failure and recovery:** Retries follow the specified backoff and three-consecutive-model-failure blocking rule. Ambiguous pushes reconcile stable operation identities against canonical history before repetition. Acknowledged drafts survive crashes before/after model work, commit, push, audit, and reporting. Missing reports replay idempotently. Startup rejects a second service instance and reconstructs state from canonical Git plus external operational records.
12. **Human controls:** Authorized drain, retry, defer, requeue, reject, adjudicate, and resume actions have distinct effects, current-state fences, and durable receipts. Active-attempt input changes return busy. Changing a blocked batch by rejection/adjudication terminally disposes of the old drain and invalidates its old proposal; untouched drafts remain pending and blocked until an explicit separately receipted resume. The old drain never retries over the human decision.
13. **Inspection confidentiality:** Manager may receive only an explicitly opened item's bounded committed text and service-authorized same-Project context. No arbitrary paths, recursive browsing, active rendering, remote-resource fetching, persistent content caches, or content-bearing replay are introduced. Manager/Hub logs, replay, and audit do not retain inspection or adjudication bodies. Reopening after reconnect requires fresh authorization; no offline view or autosaved adjudication draft is promised.
14. **Settings:** Shared ceilings, drain bounds, and secret-filter modes display their all-Projects effect and require installation-operator authority. Validated changes produce a durable version and apply atomically to new operations without restart; in-flight work retains its starting version. Invalid or absent active configuration blocks writes rather than silently reverting to defaults. Settings changes do not qualify models or authorize hosted egress.
15. **Maintenance:** Startup, successful Project changes, and explicit requests trigger bounded model-free checks over coherent snapshots. Partial coverage never means clean and cannot clear prior findings outside the checked scope. Lint neither changes content nor adds a second veto. Semantic repair uses explicit drafts; deterministic reconstruction is human-requested and limited to reproducible service-owned indexes. Unknown authored content, damaged history, stale concepts, and archived bundles are preserved.
16. **Observability and retention:** Source-tagged, timestamped observations distinguish stale, disconnected, unknown, blocked, and healthy. Audit links requests, identities, optional Runs, queue/drain/attempt IDs, configuration and Git revisions without raw content or secret matches. Notifications are metadata-only and deduplicated. History retention cannot erase unresolved/replay/deduplication state or make an old request execute again. Capacity exhaustion stops affected writes and alerts instead of silently deleting evidence.
17. **Lifecycle:** Room Stop/Destroy does not delete Library data. An independent authenticated local operator path remains available when the Room Hub is absent. Project archival rejects new captures, permits the specified single bounded final attempt, retains remaining drafts, commits archived state, and freezes content writes; restore explicitly reopens the same Project. Registration never silently restores an archive.
18. **Promotion handoff:** There is no Library export/promotion operation or cross-Project credential. Disclosure requires Project-authorized human approval of the exact package and audience; destination acceptance is a separate human decision. Private evidence remains private unless explicitly released. Project outcome records report observed acceptance and unknown adoption without automatic propagation, synchronization, rollback, or archive bypass.

## Implementation Decisions

### Authority and module ownership

Use the current domain glossary: a Deployment contains Rooms; each Room is bound to one Project; a Participant has a durable Actor Identity and a Participant Profile. Historical references to a single-Project Deployment or Deployment Profile map to the current Room/Participant Profile concepts, not new product types.

The supervisor owns approved Project bindings, mounts, authenticated endpoint provisioning, and atomic Project projection publication. Each Hub authenticates and routes typed Project operations and records safe metadata, but does not own the Library clone, credential, canonical content, model client, or synthesis decisions. The external Library Service owns validation, repository writes, scheduling, model assembly, operational receipts, and recovery. Manager is a read model and typed human command client. Participants receive only their Project projection and the permitted enqueue surface. The repository's receiving controls and qualified storage provide publication protection; external operator configuration owns credentials, provider profiles, and backups.

The singleton and its credentials are trusted infrastructure with the accepted whole-library read/write compromise scope. The deterministic gate protects Project boundaries from callers and model proposals; it does not contain a malicious host/service administrator, prove semantic truth, or undo disclosure. Sources: [Locate and lay out the per-Project OKF bundle](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/33#issuecomment-6397329269), [Choose the librarian's agent-facing interface](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/31#issuecomment-6397328044), and [Define the hosting-independent Library repository contract](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/130#issuecomment-6453919363).

### Canonical Git target and bundle identity

Configure one private canonical Git target, one canonical branch, and external credential references. Standard Git carries content; provider issues, PRs, CI, APIs, apps, and subscriptions are not Library dependencies. A host may impose its own prerequisites. Receiving-side controls must deny non-fast-forward updates and deletion across all Library branch refs through every interface available to the Library identity. Client promises are insufficient. The identity has no rule-administration, repository-deletion, protection-bypass, or direct canonical-filesystem route. Its source-reading authority grants no source-writing authority. Trusted administrators remain outside this containment claim.

A separately administered same-host bare repository can qualify; a service-owned writable directory cannot prove independent enforcement, and a second directory on one host does not establish a host-loss backup. Qualify exact policy, identity, storage, and recovery behavior before write readiness. Missing or invalidated evidence blocks writes; it never selects another host. The Library working clone is reconstructible, not the durable acceptance boundary.

Each Project is an independent OKF v0.2 bundle at `projects/<source-forge-host>/<owner>/<repository>/`. Source Forge host plus immutable source-repository identity establishes registration identity; current coordinates establish its human-readable path. Rename/transfer moves that Project directory atomically without changing Project identity or the fixed read interface. Library hosting coordinates do not replace source Project coordinates. The Library repository root holds operational documentation only and is not an OKF bundle or shared global knowledge index.

A bundle contains root `index.md` and `log.md` plus `context/`, `decisions/`, `research/`, and `pending/`. Initial concept types are `context`, `decision`, and `research`; rationale stays in its decision. Drafts retain the intended type and use OKF `status: draft`. Do not add types, directory depth, or frontmatter vocabulary speculatively. Readers tolerate unknown existing types/keys and broken links; writers remain constrained to supported v1 output. Sources: [Locate and lay out the per-Project OKF bundle](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/33#issuecomment-6397329269) as amended by [Define the hosting-independent Library repository contract](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/130#issuecomment-6453919363).

### Registration and explicit import

The initialization commit contains exactly `index.md`, `log.md`, `context/index.md`, `decisions/index.md`, `research/index.md`, and `pending/index.md`. Root index declares `okf_version: "0.2"`, records canonical source coordinates and immutable source-repository identity in its body, and links the four directories. Child indexes contain headings but no entries or frontmatter. The log records one dated Initialization entry. Registration creates no concept and never scans source documentation for knowledge.

A missing bundle is created and published atomically; acknowledgement includes its published SHA. A healthy matching retry returns it unchanged. An archived matching registration reports archived state without restoring. A conflicting identity or malformed/partial path fails closed without overwrite, merge, or silent repair.

Import is a separate preview-and-confirm operation. A human chooses an exact file manifest at a pinned source commit. Confirmation creates bounded pending concepts with intended type, draft status, generated metadata, and `sources[].resource` pinned to repository/commit/path; include source title, author, and modification date when available. Import does not imply verification: fidelity confirmation is separate. Repeating the same confirmed manifest creates no duplicates. Human confirmation cannot bypass secret policy or Project authority. Source: [Define Project library bootstrapping](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/40#issuecomment-6397336303).

### Native read interface and snapshot semantics

The Participant-facing Library projection is the fixed `library/` subtree of its approved Project reference root, recorded in the source decision as `/project/reference/library/`. Its sibling `library.snapshot.json` records Project identity, published commit SHA, and publication time. The supervisor derives the source from the Room binding; callers cannot choose source paths. Expose no canonical repository root, sibling bundles, `.git`, or Library credentials.

Publish one exact canonical commit atomically, including coherent snapshot identity. Before the first publication, the manifest has `commit_sha: null` and the bundle is absent. Registration, import, enqueue, and drain publication trigger refresh; startup/reconnect reconcile the projection. Failed refresh preserves the last coherent bundle and its original timestamp. Do not present a fabricated empty bundle, claim freshness, or inject an outage warning into Runtime context. Runtimes do not bypass the projection to read the service or repository directly.

Discovery begins with concise root/child indexes containing title, bundle-relative link, type, status, and short description; pending index exposes drafts and parked state. Do not inject Library knowledge into context. Native tools may render differently without a common search protocol. Query semantics are case-insensitive AND substring matching, with typo-tolerant token fallback only after no document matches. Label fallback FUZZY, pending DRAFT, and both when applicable. Initial results are bounded to eight matches and prioritize fragments, then optional summary, then whole-document follow-up. Whole documents preserve metadata, rationale, sources, and cross-references; material claims require opening their containing document. No result means no inferred answer.

Add no MCP read/search service, SQLite FTS, embeddings, or derived index. Reconsider retrieval only after real Project queries demonstrate unacceptable measured latency or relevance, not at a speculative document-count threshold. Sources: [Choose the librarian's agent-facing interface](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/31#issuecomment-6397328044) and [Prototype the deterministic read path](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/34#issuecomment-6397329851).

### Capture contract and two levels of idempotency

`library.enqueue` is the only new Participant-facing Library Command. Pi and Claude adapters may expose it through their native mechanisms but preserve one typed contract. It requires a current authenticated Participant badge and the Participant Profile capability `library:enqueue`; read access does not grant write access. The Hub derives Project and Actor identity. The operation is Project-scoped, not a Run lifecycle gate: originating Run is optional provenance, and retries remain valid after that Run closes. No transcript scan, Run boundary, context-reset hook, or implicit harvest enqueues material.

The caller supplies an opaque librarian request ID, intended type, human-readable title, nonempty Markdown body, and sources; `research` requires at least one source. Conflict/relationship hints are optional. The caller need not inspect pending work first. The service serializes content and supplies authenticated Project path, original Actor/Run provenance, timestamp, generated status, draft status, and stable queue identity. Raw frontmatter and caller-owned service metadata are not accepted.

| Outcome | Meaning and returned evidence |
| --- | --- |
| `DURABLY_QUEUED` | Exact draft commit published; queue ID, bundle-relative path, published SHA, current projection SHA, and whether that draft is visible in the projection. |
| `REJECTED` | Deterministic input/identity refusal with a precise non-retryable safe reason. |
| `NOT_DURABLE` | Service/transport/publication failure or uncertainty; preserve request ID and reason, with `retryable: true`; this is not proof of absence on the canonical target. |

Same librarian ID and canonical payload returns the original capture result without another commit; changed payload returns `ID_CONFLICT`. Different IDs remain different drafts even if text overlaps; synthesis, not enqueue, handles semantic duplicates. The validated queue identity determines its `pending/<id>.md` path without allowing traversal.

Each new attempt uses a new Hub Command ID and the same librarian request ID/payload. Any currently authorized Participant may retry it, while the first Actor/Run remains immutable submission origin and each attempt records its actual actor/time/Command/outcome. An exact Hub retry remains bound to its own authenticated origin; the service-level retry does not weaken the Hub's cross-Actor equality rules. If the adapter cannot reach the Hub, it claims no librarian outcome. No hidden workspace fallback or second knowledge queue exists. Sources: [Define what a Participant hands the librarian](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/35#issuecomment-6397330372) and [Choose the librarian's agent-facing interface](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/31#issuecomment-6397328044).

### Deterministic commit gate and reference-data trust

Every canonical content write validates the complete proposed Project result before publication. Derive the allowed prefix from authenticated authority; validate paths/mutations, OKF, links, indexes, log, provenance, configured bounds, and content policy. Structural failure rejects the whole proposal, not selected files. Read projections remain available when writes are blocked.

Canonical text uses UTF-8, NFC normalization, and LF endings. Reject malformed UTF-8, duplicate YAML keys, custom tags, aliases, unsafe scalar types, NULs, and disallowed controls. Normalize POSIX paths and reject traversal, repository metadata, symlinks, backslashes, controls, and normalization/case-fold collisions. Use a link parser, not regular-expression matching. Ordinary Markdown and fenced code are allowed; raw HTML, images/embeds, unsafe schemes, and external body links are rejected. Anchors and normalized bundle-relative links are allowed, including broken internal links. External references belong in sources.

Initial enqueue defaults are title 200 characters, body 16 KiB UTF-8, at most sixteen sources, and canonical payload 32 KiB. All operational ceilings are finite, versioned human settings within fixed crash-protection maxima. High-confidence credential/private-key rules may reject immediately. Heuristics start observe-only and become blocking only after fixed positive and representative false-positive corpora pass. A blocking rule cannot be bypassed; corrected content requires a new request ID. Record safe rule/location/hash evidence, never matched secrets.

Sources may name bundle concepts, source-repository artifacts at pinned commits, or HTTPS resources. Mutable external URLs remain visibly unpinned and cannot alone support machine verification. Model-bound excerpts additionally need immutable identity, an exact bounded range, and a content hash. Reject binary, symlink, submodule, archive, unsupported-encoding, oversized, unresolved, or unauthorized excerpts. A deterministic source failure makes no model call and durably parks the attributable draft with a precise reason while unrelated eligible work continues; do not silently redact or truncate.

The model returns a strict proposal manifest, not a Git diff or filesystem patch. Service code constructs files, allocates lowercase ASCII slugs with a stable queue-derived collision suffix, and generates indexes/log entries. Integration may add/update concepts only in the three accepted concept directories. Accepted concepts may be updated/deprecated, never automatically deleted/renamed; only selected pending drafts may be removed or parked. Preserve unknown existing types/keys for readers, without permitting model introduction of unsupported writer output.

The service stamps generated/lifecycle/timestamp fields. The model cannot set `verified`; an authenticated human or separately identified deterministic verifier may do so with evidence. Meaningful changes clear current verification; unchanged concepts retain it. `stale_after` comes from a human or deterministic policy, never model inference. Stale content remains readable with a warning. Integrated/stable means integrated, not true. Type, lifecycle, derived OKF trust tier, freshness, and source presence stay orthogonal.

Runtime guidance at the controlling instruction layer declares the projection reference data, unable to override Runtime, Project, or authenticated human authority. Concepts and indexes carry a deterministic reference-data notice. Instruction-like source text retained for legitimate subject matter is an attributed quotation, not instructions to the librarian. Neither fencing nor deterministic validation claims to solve semantic prompt injection or establish truth. Source: [Define the librarian's trust boundary](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/39#issuecomment-6397335804).

### Model request, qualification, and egress

The Deployment accepts externally owned provider profiles; a human-controlled Project setting selects exactly one qualified local or hosted profile. Hosted processing requires both an approved profile and explicit Project authorization. Profiles fix endpoint, region when relevant, retention, and data-use terms; they prohibit training on requests and use zero retention or the shortest explicitly accepted retention. Material model versions require qualification; changing provider or data-use terms requires renewed Project authorization. No outage, quota, capacity, malformed output, or quality problem selects another provider or local/hosted mode automatically.

Deterministic code assembles only the selected bounded drafts, necessary accepted Project indexes and context/decision/research documents excluding the log, and exact pinned source excerpts carried by those drafts. Exclude unselected pending contents, sibling Projects, Git history, audit, credentials, private sessions, unrelated files, and unapproved references. Drafts, accepted concepts, and excerpts are separate typed untrusted data; trusted instructions remain outside them. The model has no repository, network, browsing, or tools and cannot request more material. Scan the exact assembled request under the current secret policy before either local or hosted dispatch.

File-count, byte, token, batch, and excerpt ceilings are hard bounds. An oversized unit remains pending for operator handling; never create plausibly complete output from silent truncation. When inference shares hardware with interactive Participants, at most one low-priority request is admitted by the external gateway and interactive demand has priority. Capacity shortage leaves work pending; the service yields after each bounded unit rather than detecting idleness.

Every active model/material version must pass the fixed synthesis corpus: direct integration, duplicate/overlap handling, contradictions, provenance, constrained output, adversarial-source handling, and abstention when evidence is insufficient. Qualification and provider catalogue/server lifecycle remain external concerns. Interactive coding readiness is not synthesis qualification or egress permission. Source: [Bound what the Library Service may send to its model](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/37#issuecomment-6397331747), with the content boundary in [Define the librarian's trust boundary](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/39#issuecomment-6397335804).

### Scheduling, drain outcomes, and recovery

Successful enqueue marks its Project runnable after a short configured coalescing delay; explicit requests, retry deadlines, and startup reconciliation also establish eligibility. There is no separate queue-size threshold. An explicit request removes the delay but neither preempts active work nor jumps the fair queue. Choose the eligible Project least recently served, with canonical Project identity as tie-breaker. Yield after every attempt, successful or not. Backoff and BLOCKED Projects are ineligible.

Within a Project, select by durable enqueue commit order then queue ID, excluding parked drafts. One fixed batch uses one model call per attempt; later drafts wait. Defaults are eight drafts, 64 KiB of draft content, and a 120-second attempt timeout, all finite shared settings. Hold the Git write lock for reconciliation/commit/push only, not model latency; enqueues and coherent readers continue independently.

Before model work, persist drain ID, attempt, input SHA, ordered queue IDs, configuration identity, and model-input hashes in the external operational record. A valid proposal may integrate/merge some drafts and park specifically attributed unresolved contradictions in one atomic commit. Parked drafts retain draft status and durable pending-index state and are excluded until authorized handling. Uncertain attribution commits nothing and retries the fixed batch. Parking-only transitions are also durable commits. Invalid structure rejects everything.

Backoff is 5 seconds, 30 seconds, 2 minutes, 10 minutes, then 30 minutes capped; no jitter is needed for one scheduler. Repository/transport outages retry without a fixed attempt limit while independent eligible Projects continue where shared infrastructure permits. Three consecutive model timeouts or deterministically invalid outputs block the drain and Project for operator action. Ordinary drain requests cannot bypass that state. An explicit ordinary retry resumes the same drain and full selected batch with a new attempt number.

Before applying a proposal, fetch the canonical head and check the recorded input manifest. Reuse the result only when every input still matches; otherwise rerun the same fixed batch against a fresh snapshot. A compatible newer head is reconciliation, not a failed attempt. Build on the latest compatible head and publish fast-forward. Distinguish `input_sha`, actual parent `previous_sha`, and published `resulting_sha`.

Before publication there is no drain success, and acknowledged drafts remain canonical. After an ambiguous push, locate the stable drain identity in canonical history; use that committed result if present, otherwise retry the original operation after reconciliation. After push but before audit/report completion, reconstruct from Git and backfill records. Model output is ephemeral, not another recovery store. Only after resolving ambiguous publication may local-only clone state be discarded/rebuilt.

Acquire one host-local exclusive lease before touching the clone; a second process fails readiness and does no work. Startup reconciles in-flight identities, validates bundles, and rebuilds parked state, scheduling, and retry deadlines from Git plus external operational records. Project-local inconsistency blocks that Project; shared corruption or unavailable shared infrastructure stops drains. Graceful shutdown stops selecting, lets the current attempt finish within its existing bound, flushes reports, and exits; forced termination uses normal recovery.

Report STARTED, RETRY_SCHEDULED, COMMITTED with per-draft outcomes, and BLOCKED to the relevant Hub. Reports are at least once, deduplicated by drain ID and transition sequence, with the external record as replay source. Hub unavailability and absent Participants do not prevent eligible draining. The later operator-disposed terminal outcome is also reported without claiming successful model integration. Sources: [Define the singleton Library Service’s drain lifecycle](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/32#issuecomment-6397328674) and its explicit operator amendment in [Define librarian operator control and observability](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/43#issuecomment-6453421613).

### Human operations, confidential inspection, and settings

Provide a Project Library operations view in Manager and one narrow Library Settings page. Manager uses typed requests through the Room Hub; the Library Service revalidates authority and owns outcomes. A narrow authenticated host-local operator interface uses the same validation and receipts when Manager/Hub is absent, including after Room destruction. Neither interface grants raw clone editing, shell, arbitrary filesystem access, a general knowledge editor, or Participant control APIs.

An authorized human explicitly opens one pending item. The service derives permitted same-Project committed context and bounds both responses and total inspection context; no caller paths or recursive link expansion are allowed. Mark insufficient context explicitly and use authenticated local inspection when broader review is necessary. Render inert text with no automatic remote-resource fetch. Inspection responses are ephemeral, not replay events. Manager and Hub do not persist bodies in databases, replay, logs, or browser storage; this also covers the human conclusion/rationale in intermediary handling. Reconnection replays safe metadata; content needs a fresh authorized open. Canonical Git retains accepted content. No offline view or autosaved adjudication draft is promised; unsubmitted text can be lost on refresh/crash.

| Action | Contract |
| --- | --- |
| Drain | Mark eligible for one fair bounded unit, without preemption or BLOCKED bypass. |
| Retry | Explicitly resume the original blocked drain with the same complete fixed batch and a new attempt, subject to valid authority/configuration. |
| Defer | Snooze attention only; do not change draft, parking, or blocked state. |
| Requeue | Release eligible parked work only after its recorded prerequisite is resolved; do not bypass an unresolved contradiction or Project block. |
| Reject | Commit a reasoned disposition removing the item from current pending work while preserving history. |
| Adjudicate | Commit the human's authoritative conclusion and rationale with deterministic formatting/provenance, never model reinterpretation or validation bypass. |
| Resume remaining work | After a blocked-batch disposition, separately recheck blockers and release retained work for a newly identified fairly scheduled drain. |

Any content action against an active attempt's selected inputs returns busy; refresh after the bounded attempt rather than queueing a blind write. If reject/adjudicate changes a blocked batch, the same durable Git transition records outcomes and terminally marks the original drain operator-disposed, retaining original batch identity and invalidating its uncommitted output. Untouched drafts remain pending and the Project blocked. Only a separately receipted resume releases them; a new drain ID is used and an empty remainder makes no model call. The disposed drain never resumes or overwrites the human decision. This does not prohibit separately authorized future submissions.

All actions bind the human, authorized Project or shared-settings scope, unique request ID, inspected target/content versions, and relevant configuration version. Stale state requires refresh, not force. Reuse under different payload is rejected; same request cannot repeat a write. An unknown response remains unknown until authoritative reconciliation. Content/disposition success cites the pushed commit; settings success cites a durable configuration version; attention/scheduling success cites an operational acknowledgement, not an invented Git commit.

Ceilings, drain bounds, and filter modes stay shared at Library Service/deployment scope, with visible all-Projects impact and installation-operator authority; add no per-Project overrides. Shared-settings authority grants no cross-Project content access. Validated updates apply atomically without restart to new operations; current operations retain starting versions. Audit actor/time, old/new configuration hashes, changed keys, version, and validation outcome. Missing, malformed, or unsafe active configuration blocks writes. Provider selection/qualification and Project egress remain separate; settings do not provision providers or create silent fallback. Source: [Define librarian operator control and observability](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/43#issuecomment-6453421613).

### Lint and maintenance

Check coherent accepted/pending/parked documents, indexes, and log using the existing deterministic validators. Rule violations differ from observations: malformed structure or missing required index entries can be errors; broken internal links, elapsed freshness, isolated concepts, and missing optional sources do not prove false knowledge. Unknown existing OKF types/keys remain tolerated. Lint adds no second write veto and a clean report proves no semantic truth.

An isolated concept has no incoming links from other accepted concept documents, excluding generated indexes, pending drafts, and log; missing index membership is separate. Stale means a recorded freshness policy elapsed, not false. A broken reference has no target; a link nobody wrote is a semantic suggestion. Provenance mismatch requires available pinned material to disagree with its recorded hash/range; absent material is not checked and inaccessible material is unavailable. Lint fetches no external sources. A branch advancing does not invalidate an old commit pin, and source availability does not renew verification.

Semantic correction is an ordinary explicit human/Participant draft naming the concepts, suspected problem, and available sources. The scanner creates no drafts automatically. A suspicion is not evidence; integration may propose supported corrections/cross-references/merges under the normal request and gate, otherwise abstain or park. This does not add human approval to every ordinary integration.

The separate human-requested deterministic repair route rebuilds only service-owned indexes fully reproducible from canonical documents and queue state. Preserve authored or uncertain material and report it rather than replacing it. Do not fabricate log history. Both repair routes use the normal Project gate, input-change checks, fair bounded lifecycle, fast-forward publication, and audit. No automatic accepted-concept deletion/rename, age-based deprecation, pin replacement, self-verification, or freshness renewal is allowed. Archived Projects permit read-only checks, not repairs.

Run checks at startup, after successful Project changes, and explicitly on request; coalesce redundant work, use finite configured bounds, and do not hold the Git write lock while inspecting. No periodic maintenance timer exists in v1: quiet bundles receive no new concept-age report until another check. This does not remove the separate queue-age warning. Partial/interrupted scans record coverage and unchecked areas, cannot report overall cleanliness, and never weaken complete write validation.

Reports contain Project/scan identity, input SHA, time, configuration/rule versions, coverage, finding codes, safe locations, hashes, and resulting draft/repair references. No raw content or secret matches enters audit. An old-SHA report is historical. Correlate repeated findings by Project, rule, location, and relevant hashes; changed content/rules need reassessment and partial scans cannot clear unexamined findings. Operator controls own display, access, alerts, and retention. Source: [Define the librarian's lint and maintenance pass](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/44#issuecomment-6453460536).

### Observability, audit, and retention

Show active/parked depth, oldest age, throughput, drain/attempt and next retry, capture/source/model/validation/transport/audit/recovery failures, adjudication wait, canonical/projected SHAs, projection freshness, replay lag, and literal provider observations. Every observation retains owner, time, and stale/unknown state. Empty queues do not establish successful capture. Effectiveness indicators are observed duplicate merges and human-recorded corrections with denominators and observation windows; missing feedback is not measured, not a quality score.

Enqueue evidence includes Project/request/Command IDs, actual and original identities, optional originating Run, canonical payload hash/size, configuration version, rule results, outcome, queue path, and published SHA. Integration evidence adds drain/attempt, input SHA, queue IDs, profile identity/local-or-hosted mode, exact source/input/proposal hashes and sizes, touched paths, outcomes, and resulting commit. Settings and human dispositions retain their authentic authority, version, and outcome evidence. Titles/bodies, prompts, rejected model output, and matched secrets are not telemetry labels or external audit payloads. Refusals expose stable safe reason, field/source, rule, and location without echoing a matched value.

Keep persistent Manager attention for parked conflicts and actionable failures. Gotify follows existing preferences with bounded sanitized metadata and source links only. Default to one deduplicated notification for a newly blocked Project or audit/storage/recovery failure, not each draft or retry. Parked conflicts appear in Manager without default external notification. Initial oldest-draft warning is a configurable 24 hours, a tuning default rather than a service guarantee. Snoozing never resolves the underlying state.

Use configured Deployment audit retention/byte limits for operational history and derived time-window statistics, without another monitoring store. Preserve unresolved operations and undelivered reports until safe settlement. Completed detailed receipts may expire, but retain enough durable identity/digest/outcome reference to reject replay; an old request then reports already handled/detail expired, never performs another write. Ordinary display retention does not govern recovery or deduplication. Do not automatically prune canonical Git history. Required-state capacity exhaustion stops affected writes and alerts rather than erasing evidence. Source: [Define librarian operator control and observability](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/43#issuecomment-6453421613).

### Project lifecycle and private promotion handoff

Room stop/destruction leaves Library content unchanged; a running Hub remains available after Stop, and the separate operator path covers a destroyed/absent Hub. Project archival rejects enqueues, waits for the active global attempt, permits one bounded model attempt over one batch without repeating failed model work, retains remaining drafts, and commits archived state. Only publication Git operations retry as needed. Further content writes freeze. Restore explicitly reopens the same Project directory and pending work; nothing automatically deletes or relocates history. Sources: [Locate and lay out the per-Project OKF bundle](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/33#issuecomment-6397329269) and [Define the singleton Library Service’s drain lifecycle](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/32#issuecomment-6397328674).

Promotion is an ordinary contribution to the existing sandbox-guidance owner, not a Library command, queue, export button, global store, or credential. Preparation stays within existing Project processing/tool permissions. Before any disclosure, a Project-authorized human approves the exact package and audience, including text, attachments, links, metadata, identities, and evidence; changed material/audience requires renewed approval. The destination's authorized human separately reviews and accepts/rejects correctness, generality, safety, and consistency. One person may hold both responsibilities, but both decisions are explicit. Reading/operator/model permission does not confer disclosure authority; uncertainty keeps the package private and secret restrictions cannot be bypassed.

Keep a private source trail in existing records: original concept/Library commit, source pins, reason to generalize, limitations, exact sanitized version, and actual disclosure approval. Send only approved standalone guidance, rationale, conditions, and permitted evidence; public destinations receive public references only. Project identities, private paths/links/hashes/excerpts are not implicitly public after rewording. Additional evidence needs approval or an independent reproducible substitute; otherwise defer/reject.

Capture observed outcomes through an ordinary Project decision draft, preserving source/package versions, genuine approval reference, destination reference, and review/commit evidence. Agent prose is not approval authority. Use plain-language proposed/submitted/accepted upstream/rejected/deferred/adoption unknown outcomes without a lifecycle service or watcher. Failed capture or an archive freeze leaves the outcome unrecorded and reported; it does not undo the destination outcome or authorize bypass. Keep original knowledge/history. Destination acceptance is not rollout: confirm activation with that owner. Corrections require another authorized handoff and independent Project correction; no automatic synchronization, rollback, or reseeding guarantee exists. Source: [Define the handoff for promoting Project knowledge into sandbox-wide guidance](https://github.com/matuto-ai/ultimate-agent-sandbox/issues/131#issuecomment-6453915947).

## Risks and Mitigations

- **Low actual value or capture adoption:** historical volume is small and the cross-Runtime-value assumption is unverified. Keep explicit capture, native lookup, no memory engine, no automatic harvest, and literal outcome indicators; revisit only after observed use demonstrates a missing capability.
- **Plausible but wrong synthesis or instruction-like sources:** use pinned provenance, separate untrusted fields, qualified models, deterministic structural checks, orthogonal trust/freshness, abstention, and human adjudication. Do not claim these prove truth or eliminate semantic prompt injection.
- **Acknowledgement or replay loss:** canonical Git identities, immutable librarian IDs, external operational records, atomic dispositions, input manifests, and qualified restart/restore evidence prevent duplicate or resurrected work. Unknown external outcomes remain unknown until reconciled.
- **Shared-service compromise or availability:** credential isolation, Project-bound requests, one writer/lease, narrow receiving authority, fair bounded scheduling, and independent backups limit ordinary failures. The accepted shared-service/host compromise scope and shared-infrastructure outage remain visible risks, not per-Project isolation guarantees against the administrator.
- **Growth beyond bounded model/storage capacity:** hard finite limits preserve honest failure instead of silent truncation/deletion. Oversized work stays pending for handling; necessary recovery records can exhaust capacity and require operator action. No speculative sharding, summarization pipeline, automatic pruning, or generalized engine is added.
- **Manager disclosure and intermediary leakage:** explicit bounded opens, typed authority, inert rendering, metadata-only replay/audit, and tests of real persistence surfaces constrain exposure. No offline/autosave convenience is promised; unsubmitted decisions may be lost.
- **Hosting neutrality mistaken for universal compatibility:** require evidence for the actual receiving policy and storage, not brand approval. Same-host targets are conditional and do not provide host-loss backups by themselves; unmet qualification blocks writes.
- **Stale diagnostics or incomplete promotion follow-through:** reports retain snapshot/time/coverage, partial checks cannot clear unseen findings, and manual handoffs record only observed outcomes. Quiet bundles and downstream adoption/corrections may remain unobserved; there is no watcher or continuous semantic assurance claim.
