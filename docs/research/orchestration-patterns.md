# Research: useful orchestration patterns from cmux and peer-agent systems

## Summary
The strongest reusable pattern is a visible, addressable session fabric: every agent gets a named long-lived session, a stable address, resumable state, and observable events/notifications. Cmux contributes the operator-facing control plane for visible panes, layouts, notifications, and restore, while Pi and the `pi-vs-claude-code` experiments contribute direct peer messaging and machine-readable event streams; together they support a flat or lightly hierarchical team, not hidden background swarms or mandatory manager trees.

## Findings
1. **Visible, addressable long-lived sessions are the foundation, not an add-on.** The companion repo states the key requirement as “real, addressable terminals (`surface:3`)” rather than “SDK abstraction over hidden processes,” and cmux exposes both CLI and Unix-socket control over workspaces/surfaces. Official restore docs add that cmux restores layout, cwd, scrollback, browser state, and can resume supported agents from native session IDs such as `pi --session <id>`. This is direct evidence for adopting explicit session identities and against hidden-agent orchestration. [learning-cmux README](https://github.com/disler/learning-cmux-with-agents/blob/main/README.md) [cmux API docs](https://cmux.com/docs/api) [cmux session restore docs](https://cmux.com/docs/session-restore)
2. **Direct peer communication should be first-class and addressable, not mediated through terminal scraping.** `extensions/coms.ts` implements same-machine peer messaging where each agent binds one endpoint and discovers peers through per-project registry files under `~/.pi/coms/projects/<project>/agents/<name>.json`. `extensions/coms-net.ts` keeps the same user model but swaps transport to an HTTP/SSE hub, with explicit tools for list/send/get/await; `scripts/coms-net-server.ts` confirms the hub protocol and SSE streams. This is direct evidence for named peer mailboxes/registries and against screen scraping as the canonical transport. [coms.ts](https://github.com/disler/pi-vs-claude-code/blob/main/extensions/coms.ts) [coms-net.ts](https://github.com/disler/pi-vs-claude-code/blob/main/extensions/coms-net.ts) [coms-net-server.ts](https://github.com/disler/pi-vs-claude-code/blob/main/scripts/coms-net-server.ts)
3. **Declarative rosters/layouts are a better team bootstrap than imperative pane setup.** `prompts/09-declarative-boot.md` defines layouts as code and shows `workspace create --layout`; `cmux/fs-team.layout.json` encodes a five-agent roster (`lead`, `plan`, `build-be`, `build-fe`, `test`) with startup commands per pane; the README calls this “one declarative file” for instant team startup. That is direct evidence for checked-in roster/topology files. [09-declarative-boot.md](https://github.com/disler/learning-cmux-with-agents/blob/main/prompts/09-declarative-boot.md) [fs-team.layout.json](https://github.com/disler/learning-cmux-with-agents/blob/main/cmux/fs-team.layout.json) [learning-cmux README](https://github.com/disler/learning-cmux-with-agents/blob/main/README.md)
4. **Event streams should carry machine events; free-form terminal content should stay a fallback.** The cmux pattern doc is explicit: completion/attention signals should come from `cmux events`, `notification.created`, and `wait-for`, while `read-screen` is only the “honest fallback” for free-form content. Pi’s official `--mode json` emits JSONL session headers and typed lifecycle/tool events. This supports a split design: event bus for state changes, text reads only for human-facing output or non-instrumented tools. [PATTERNS-read-and-notify.md](https://github.com/disler/learning-cmux-with-agents/blob/main/prompts/PATTERNS-read-and-notify.md) [Pi JSON event stream docs](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/json.md)
5. **Notifications should be durable, routable, and tied to addresses.** Cmux notifications have a lifecycle (received/unread/read/cleared), unread workspace badges, jump shortcuts, custom commands, and hookable policy transforms; the pattern doc recommends using notifications/events as the “doorbell” and then reading the relevant surface for details. This is direct evidence for durable notification records keyed by workspace/surface IDs rather than ephemeral stdout polling. [cmux notifications docs](https://cmux.com/docs/notifications) [PATTERNS-read-and-notify.md](https://github.com/disler/learning-cmux-with-agents/blob/main/prompts/PATTERNS-read-and-notify.md)
6. **Restoration should rebuild topology first, then resume sessions by native IDs.** Cmux’s official restore model is explicitly two-phase: rebuild windows/workspaces/panes from snapshot, then run agent-native resume commands if enabled. The companion prompt `24-crash-proof-resume-the-fleet.md` operationalizes the same pattern for fleets. That is direct evidence for separating topology restore from agent/session restore. [cmux session restore docs](https://cmux.com/docs/session-restore) [24-crash-proof-resume-the-fleet.md](https://github.com/disler/learning-cmux-with-agents/blob/main/prompts/24-crash-proof-resume-the-fleet.md)
7. **Configurable team topology should be allowed, but hierarchy should be optional.** The companion repo demonstrates a 3-tier orchestrator → lead → worker layout in `fs-team.layout.json`, and the video summary says the demo uses that structure while keeping “a flat communication channel where any agent can prompt any agent.” This is mixed evidence: the three-tier shape is demonstrated directly in the repo, while “flat communication channel” comes from the video summary tied to the exact URL because the transcript was unavailable. The reusable mechanism is topology as data plus direct peer reachability, not enforced hierarchy. [fs-team.layout.json](https://github.com/disler/learning-cmux-with-agents/blob/main/cmux/fs-team.layout.json) [learning-cmux README](https://github.com/disler/learning-cmux-with-agents/blob/main/README.md) [video summary](https://openclawdatabase.com/news/videos/2026-07-06-cmux-multi-agent-orchestration/)
8. **Per-agent identity should be explicit in both registry and UI.** Cmux’s pane-identity prompt uses tab names, banners, prompts, and flashes because panes do not have intrinsic per-pane color fields. Pi peer extensions also register name, purpose, model, color, cwd, and project in their agent cards/registry. This is direct evidence for a roster schema that includes operational identity, not just a process ID. [31-identify-individual-panes.md](https://github.com/disler/learning-cmux-with-agents/blob/main/prompts/31-identify-individual-panes.md) [coms.ts](https://github.com/disler/pi-vs-claude-code/blob/main/extensions/coms.ts) [coms-net.ts](https://github.com/disler/pi-vs-claude-code/blob/main/extensions/coms-net.ts)

## Recommended reusable mechanisms
1. **Session registry** — stable session ID, human name, role/purpose, cwd/worktree, model, status, transport address, resumable native session ID.
2. **Dual control plane** — machine API for create/send/read/close/list plus human-visible panes/tabs for inspection and intervention.
3. **Declarative roster/topology files** — checked-in team definitions that encode agent roster, startup command/profile, layout, and optional adjacency/permissions.
4. **Native peer transport** — same-machine local IPC plus optional network hub; messaging address should be session/agent identity, not “whatever text is on screen.”
5. **Structured event stream** — JSONL/NDJSON events for lifecycle, tool/task status, queue depth, notifications, and restore.
6. **Durable notifications** — event + stored record + jump target, not just a toast.
7. **Two-phase restore** — restore topology, then resume session-capable agents.
8. **Topology freedom** — support flat teams, bounded leader-worker teams, and race patterns from the same substrate.

## Explicit rejects
1. **Reject terminal-screen scraping as canonical transport.** Cmux’s own pattern guide treats screen reads as fallback for free-form content; Pi peer systems implement real registries and transports instead. Keep screen reads only for observability or last-mile compatibility. [PATTERNS-read-and-notify.md](https://github.com/disler/learning-cmux-with-agents/blob/main/prompts/PATTERNS-read-and-notify.md) [coms.ts](https://github.com/disler/pi-vs-claude-code/blob/main/extensions/coms.ts)
2. **Reject hidden agents.** The companion README explicitly argues for “real, addressable terminals” instead of hidden processes. Hidden workers remove inspectability, interruptibility, and operator trust. [learning-cmux README](https://github.com/disler/learning-cmux-with-agents/blob/main/README.md)
3. **Reject token-maxing fanout as the default strategy.** The video framing argues against “token-maxing” and the concrete examples use bounded, named teams or explicit races with operator visibility, not unbounded background spawn. This point is weaker than the repo/docs evidence because the transcript was unavailable; it is supported mainly by the YouTube/search framing and the bounded rosters in the companion repo. [YouTube URL](https://www.youtube.com/watch?v=WAFUMBLOjHo) [fs-team.layout.json](https://github.com/disler/learning-cmux-with-agents/blob/main/cmux/fs-team.layout.json)
4. **Reject mandatory hierarchy.** A 3-tier topology is useful, but the demonstrated channel is still peer-addressable and the Pi peer transports are flat by design. Hierarchy should be one selectable policy, not a substrate constraint. ## Gaps
- The exact YouTube transcript was not accessible from the tooling, so video-only claims are backed by the companion repo and one secondary summary page instead of direct transcript quotes.
- I did not verify whether cmux exposes a first-party structured event stream for all surface state changes beyond the docs/examples cited; if needed, inspect the live CLI/API behavior next.
- I did not inspect the full `pi-vs-claude-code` implementation details for message durability/ordering guarantees beyond the architecture comments and server protocol framing.

## Decision implications for this spike
- **Build around named sessions, not anonymous jobs.** Session identity, addressability, and restore should be core data model fields.
- **Separate transport from observability.** Use a real peer/event transport; keep terminal reads for inspection and compatibility only.
- **Make topology declarative and optional.** Encode teams as roster files with selectable shapes; do not hardwire manager trees.
- **Treat notifications and restore as first-class orchestration features.** Without durable doorbells and resumable sessions, long-lived multi-agent work will degrade into babysitting.
- **Bound concurrency by explicit roster/race policy.** Prefer visible, named teams and explicit race groups over hidden, unlimited fanout.
