# Research: Validate neutral communication adapters for Pi and Claude Code

## Summary
Pi already exposes a stable adapter surface for a neutral Hub: JSON RPC/JSONL event streaming, durable sessions, extension hooks, correlated request IDs, queued message injection, and restart-safe extension state. Claude Code can meet most of the same needs without API-priced agents by combining first-party headless/session features with MCP servers/channels and background sessions, but its stable machine-facing surface is narrower: MCP plus `claude -p`/`stream-json`/session resume are solid; terminal automation, TUI scraping, and hook-only pseudo-daemons are not.

The safest cross-CLI design is a small hub protocol built around peer registration, peer discovery, correlated message delivery, async reply correlation, presence/attention state, and resumable session identity. Pi can implement that as an extension or RPC client directly; Claude Code should implement it through an MCP server with optional channel notifications, preserving Claude.ai/Pro/Max/Team/Enterprise subscription auth rather than requiring API-billed SDK agents.

## Findings
1. **Pi has a documented, stable headless control plane with correlation and async injection.** Pi RPC mode is a JSON-over-stdin/stdout protocol with request `id` correlation, streamed events, `prompt`/`steer`/`follow_up` commands, and persistent sessions via `--session`, `--continue`, and `--resume`-style session controls. Its JSON event mode also emits lifecycle and queue events (`agent_start`, `turn_*`, `message_*`, `tool_execution_*`, `queue_update`) that are sufficient to drive hub presence and message routing. [Source](file:///usr/local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md) [Source](file:///usr/local/lib/node_modules/@earendil-works/pi-coding-agent/docs/json.md) [Source](file:///usr/local/lib/node_modules/@earendil-works/pi-coding-agent/README.md)
2. **Pi extensions support long-lived adapters better than terminal automation.** Pi extensions can start resources on `session_start`, clean them up on `session_shutdown`, inject correlated messages with `pi.sendMessage()`/`pi.sendUserMessage()`, and persist adapter state across restart with `pi.appendEntry()` plus replay from `ctx.sessionManager.getEntries()`. `agent_start`/`agent_settled` and `ctx.isIdle()` give a clean attention/idle signal for hub presence updates. [Source](file:///usr/local/lib/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md)
3. **Pi already uses versioned neutral-ish extension protocols in `pi-subagents`, which is good evidence the host is adapter-friendly.** `pi-subagents` exposes a versioned delegation event contract and a versioned background-work provider registry shared through `Symbol.for(...)`; both are reload-safe and session-aware. That shows Pi’s extension model already supports local, process-wide registries, wake channels, active-work snapshots, and async reconciliation without shell scraping. [Source](file:///home/node/.pi/agent/npm/node_modules/pi-subagents/src/api/delegation.ts) [Source](file:///home/node/.pi/agent/npm/node_modules/pi-subagents/src/api/background-work.ts) [Source](file:///home/node/.pi/agent/npm/node_modules/pi-subagents/README.md)
4. **Claude Code’s stable local automation surface is headless CLI plus session resume, not plugin internals.** First-party docs support `claude -p`, `--output-format json|stream-json`, `--input-format stream-json`, `--continue`, `--resume`, `--session-id`, and streaming subagent output correlation with `parent_tool_use_id`. Those are stable for scripted runs and resumable conversations. [Source](https://docs.anthropic.com/en/docs/claude-code/cli-usage) [Source](https://docs.anthropic.com/en/docs/claude-code/headless) [Source](https://docs.anthropic.com/en/docs/claude-code/sdk)
5. **Claude Code can preserve subscription auth; avoid API-priced SDK agents unless explicitly wanted.** Claude Code supports Claude.ai Pro/Max subscription login, Team/Enterprise login, and long-lived subscription OAuth via `claude setup-token`/`CLAUDE_CODE_OAUTH_TOKEN`. Anthropic explicitly documents that the Agent SDK is for programmable agents and also distinguishes CLI/subscription auth from API-key auth; bare mode does not read the subscription OAuth token. For this ticket’s constraint, prefer normal Claude Code login or `CLAUDE_CODE_OAUTH_TOKEN`, not Agent SDK/API-key deployments. [Source](https://docs.anthropic.com/en/docs/claude-code/authentication) [Source](https://docs.anthropic.com/en/docs/claude-code/headless)
6. **Claude Code’s best-supported hub integration point is MCP, especially for inbound notifications.** Anthropic’s MCP docs say Claude Code can connect to MCP servers, dynamically refresh tools/resources/prompts, automatically reconnect HTTP/SSE MCP servers, and let MCP servers act as channels that push messages directly into a session when enabled with `--channels`. That is the cleanest first-party route for neutral hub registration, peer discovery, outbound send tools, and inbound message delivery without scraping the terminal. [Source](https://docs.anthropic.com/en/docs/claude-code/mcp) [Source](https://docs.anthropic.com/en/docs/claude-code/cli-usage)
7. **Claude Code supports long-lived background sessions and restart/reconnect semantics, but the external control plane is weaker than Pi’s RPC.** Agent view/background sessions keep working without a terminal, persist state on disk, survive supervisor restarts and machine sleep, and can be resumed/reattached later. Docs expose human-readable state buckets (`Working`, `Needs input`, `Idle`, `Completed`, `Failed`, `Stopped`), which are enough conceptually for hub presence, but Anthropic does not document an equivalent rich local RPC protocol like Pi’s. [Source](https://docs.anthropic.com/en/docs/claude-code/agent-view) [Source](https://docs.anthropic.com/en/docs/claude-code/cli-usage)
8. **Claude hooks are useful glue, but not the primary long-lived adapter transport.** Hooks fire at stable lifecycle points (`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStart`, `SubagentStop`, `TeammateIdle`, etc.) and can run async command hooks. That makes them good for audit, policy, or one-shot notifications to a hub, but they are per-event handlers, not a durable bidirectional session bus. They also deliver async output only on a later turn unless an `asyncRewake` path is used. [Source](https://docs.anthropic.com/en/docs/claude-code/hooks)
9. **Claude plugins are real first-party packaging, but they are not the smallest or safest adapter surface.** Official sources describe plugins as bundles of skills, agents, hooks, commands, and optional MCP config; the repo examples confirm that structure. For a neutral hub adapter, plugins are useful distribution packaging, but the runtime integration still bottoms out in hooks/MCP/commands rather than a documented equivalent of Pi’s extension API. [Source](https://docs.anthropic.com/en/docs/claude-code/settings) [Source](https://github.com/anthropics/claude-code/blob/main/plugins/README.md)
10. **The smallest cross-CLI protocol surface is narrow and should avoid tool/runtime coupling.** A shared Hub only needs: `(a)` `register(sessionId, agentId, capabilities, resumable)`; `(b)` `discoverPeers(filter)`; `(c)` `deliver(messageId, correlationId, from, to, body)`; `(d)` `ack/reply(messageId|correlationId, body)`; `(e)` `presence(state, attention, lastSeen, sessionId)`; `(f)` `recover(sessionId, cursor)` for restart replay. Pi can back these with extension state or RPC; Claude can back them with MCP tools plus channel notifications and persisted session IDs. Anything beyond that starts depending on CLI-specific UX or tool semantics. [Source](file:///usr/local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md) [Source](file:///usr/local/lib/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md) [Source](https://docs.anthropic.com/en/docs/claude-code/mcp) [Source](https://docs.anthropic.com/en/docs/claude-code/headless)
11. **Stable vs brittle boundary is clear.** Stable: Pi RPC/JSON/events/extensions/session files; Claude headless CLI/session resume/background sessions/MCP/channels/hooks. Brittle: terminal keystroke automation, parsing fullscreen TUI output, screen-scraping agent view, relying on undocumented plugin internals, or using API-priced Agent SDK/managed agents when the requirement is subscription-authenticated CLI use. [Source](file:///usr/local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md) [Source](https://docs.anthropic.com/en/docs/claude-code/headless) [Source](https://docs.anthropic.com/en/docs/claude-code/agent-view) [Source](https://docs.anthropic.com/en/docs/claude-code/authentication)

## Gaps
- Anthropic docs in hand do not show a documented local RPC/control API equivalent to Pi’s; if one exists, it was not surfaced from first-party pages fetched here.
- I did not find a first-party machine-readable agent-view/status API suitable for polling hub presence; current evidence is background-session behavior plus human-facing state docs.
- Plugin runtime docs were partially discoverable through settings and repo examples but not through a fetchable dedicated docs page in this environment.

Suggested next steps:
- Prototype Claude’s side as an MCP server/channel first, not as hooks or TUI automation.
- Keep Pi’s side as an extension first, with RPC only for external supervisors.
- Only add terminal automation after proving a hard gap in MCP/channel behavior.

## Decision implications
- **Recommended architecture:** neutral Hub service with two adapters: Pi extension adapter; Claude MCP adapter.
- **Why:** this keeps both sides on documented, restart-safe, subscription-compatible surfaces.
- **Do not lead with:** Claude Agent SDK, managed agents, or API-key-only paths; those widen scope into paid API orchestration.
- **Protocol choice:** keep the hub contract tiny and transport-agnostic; map Pi `steer/follow_up` and Claude channel/tool delivery onto the same correlation envelope.
- **Attention model:** normalize to `working | idle | needs-input | completed | failed | stopped`; Pi can derive this from lifecycle events, Claude from background-session/hook/MCP context.

## Prototype risks
- **Claude inbound push risk:** MCP channels are the clean answer, but channel support is still described as preview/research-preview in CLI docs, so availability/policy gating may vary by environment. [Source](https://docs.anthropic.com/en/docs/claude-code/cli-usage)
- **Claude presence risk:** no documented local RPC means status may be coarser or harder to automate than Pi unless MCP/channel-side instrumentation is added.
- **Hook misuse risk:** treating hooks as a bidirectional bus will create racey, turn-coupled behavior.
- **Auth risk:** `--bare` skips subscription OAuth token use, so scripted Claude runs that need subscription auth must avoid `--bare` or use a different credential path. [Source](https://docs.anthropic.com/en/docs/claude-code/authentication) [Source](https://docs.anthropic.com/en/docs/claude-code/headless)
- **Session recovery asymmetry:** Pi gives direct session-file semantics; Claude gives session/background persistence but less documented low-level recovery control.
